## ① Issueとボード

### Issueの書き方

- **1件1テーマ。** 「あれもこれも」を1件に入れない(入れると、完了が分からなくなる)
- **完成の条件**を、確認できる形で書く。「動いた」でなく「何が見えれば完了か」
- **ラベル**は種類だけ付ける: `enhancement`(機能・改善)・`bug`(バグ)・`chore`(雑務)・`docs`(文書)。状態はラベルでなく**ボードの列**で表す
- テンプレートを用意した: `.github/ISSUE_TEMPLATE/task.md`(やること)、`bug.md`(バグ)
- PRの説明に `Closes #番号` と書くと、マージでIssueが自動で閉じる(`.github/pull_request_template.md`)

### カンバン(GitHub Projects)

| 列 | 意味 | 入る条件 |
|---|---|---|
| **未着手** | やると決めたが、まだ始めていない | Issueを作ったら、まずここ。上ほど優先 |
| **作業中** | いま手を動かしている | **同時に2件まで**(増やすと、どれも終わらない) |
| **完了** | 完成の条件を全部満たした | マージして、**本番デプロイの成功まで**確認できたら |

- 作り方: リポジトリの「Projects」→ 新規 → ボード形式 → 列を上の3つにする → Issueを追加。GitHubの自動化で、Issueが閉じたら「完了」へ動かす
- 動かす人は、作業する人。毎日1分、ボードを見て、止まっているカードがないか確かめる
- スプリント(第87課題)のときは、「今週やるIssue」だけを「未着手」の上に並べる

## ③ 残すルール

`docs/team-conventions.md` の **4章** に入れた(1か所に書くため、ここには要点だけ)。

| 残すもの | 残す場所 |
|---|---|
| やること・バグ・要望 | GitHubのIssue |
| 進み具合 | ボード(未着手／作業中／完了) |
| 動かし方・全体像 | README |
| 機能の仕様 | `docs/spec.md` |
| 大きな設計判断 | `docs/adr/` |
| 変更履歴 | PRの説明とコミットメッセージ(`CHANGELOG.md` は作らない) |
| 障害・失敗 | `docs/postmortem-*.md` |
| 秘密(鍵・パスワード) | **どこにも残さない**(`.env` と、サービス側の環境変数だけ) |

**4つの原則:** ① 1か所に書く ② READMEは入り口(長くしない) ③ 決めたらその日に書く ④ 古くなったら直すか消す
