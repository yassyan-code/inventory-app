# 信頼性を数字で決める（第66課題・SLO / SLI / 可観測性）

構成は `architecture.md`、落ちる場所は `spof.md`、障害時の手順は `incident-runbook.md`。

## ① 目標（SLO）と指標（SLI）

「月に何分の停止なら許せるか」から逆算した。

| # | 守りたいこと | SLI（何を測るか） | SLO（目標） | 30日で許せる失敗 |
|---|---|---|---|---|
| 1 | 画面が開く | 本番 `/` が 200 を返した測定の割合 | **99.5%** | 約3時間36分（216分） |
| 2 | データ基盤に繋がる | Supabase の REST が応答した（200 or 401）測定の割合 | **99.5%** | 約3時間36分（216分） |
| 3 | 画面が速い | `/` が成功し、かつ 1秒未満だった測定の割合 | **95%** | 測定の5%（約36時間分） |

### なぜこの数字か
- **99.9%（月43分）にしない**: Railway は1台・1リージョン、Supabase は Free プラン（`spof.md`）。再デプロイの数秒〜数十秒の断が数回あるだけで 43分は消え、守れない目標になる。守れない目標は誰も見なくなる。
- **99.5%（月3.6時間）にする**: 利用は営業時間中の在庫操作が中心で、数分の断は再読み込みで回復する。月3〜4時間までなら業務に支障が出ないと判断した。実績を見て、守れ続けるなら 99.9% に上げる。
- **「繋がる」は 401 も成功扱い**: 鍵なしでアクセスすると Supabase は 401 を返す。サーバーが生きている証拠なので成功とする。停止中（paused）は 401 にならず失敗になる（`spof.md` の2026-10-06の件）。
- **測らないもの**: ログインや在庫更新の成功率は、ユーザーの鍵が要るので外からは測れない。アプリ内の `error_logs`（第53課題）が補う。将来の課題。

## ② 見える状態（可観測性）

外から測る → 記録する → 計算する → 画面に出す、の一本道。

```
 scripts/sre/probe.mjs   本番に GET して { 時刻, 成否, ステータス, ms } を data/probes.jsonl に追記
        ↓
 scripts/sre/slo.mjs     SLI・エラーバジェット・燃焼率を計算（純粋な関数。テスト7件）
        ↓
 scripts/sre/report.mjs  文字で表示 ＋ docs/slo-dashboard.html（画面）を書き出す
```

- 実行: `node scripts/sre/probe.mjs --count 20 --interval 6`（測定）→ `node scripts/sre/report.mjs --html docs/slo-dashboard.html`（表示）
- 画面: `docs/slo-dashboard.html`（ブラウザで開く。SLI・バジェット残り・燃焼率・応答時間の棒グラフ）
- 既にある見える化との役割分担:

| 仕組み | 見えるもの |
|---|---|
| Uptime Kuma（第53課題） | 落ちた瞬間の通知（短い間隔の死活監視） |
| `error_logs` テーブル | 画面内の未処理エラー（真っ白など） |
| Verify Railway Deploy | 本番に新版が反映されたか |
| **今回の probe/report** | 「この30日で目標を守れているか」の数字 |

### 用語（この資料での意味）
- **エラーバジェット**: 目標を守ったまま使ってよい失敗の量。99.5% なら全測定の0.5%。
- **燃焼率**: バジェットを「予定の何倍の速さ」で使っているか。1倍なら30日でちょうど使い切る速さ、14.4倍なら約2日、6倍なら5日で使い切る。

## ③ 守り方（運用ルール）

`report.mjs` が自動で判定する（`slo.mjs`）。測定が5件未満のときは「データ不足」とし、少ないデータで騒がない。

| 状態 | 条件 | どう気づく | 手を打つ |
|---|---|---|---|
| 正常 | バジェット残り25%以上、燃焼率が低い | 週1回 report を見る | 通常のリリースを続ける |
| 注意 | 6時間の燃焼率が6倍以上 ／ バジェット残り25%未満 | report の表示。Uptime Kuma の断続的な DOWN | 今日中に原因を調べる。リリースは小さく慎重に |
| 緊急 | 1時間の燃焼率が14.4倍以上（今まさに落ち続けている） | Uptime Kuma の通知 → すぐ report で確認 | `incident-runbook.md` を開始。原因が直近のリリースなら Railway で前の版に戻す。Supabase が paused なら Restore |
| 凍結 | バジェット超過（目標を割った） | report の表示 | 新機能のリリースを止め、信頼性の修正だけ行う。原因をポストモーテムに書く（`postmortem-*.md` の形式） |

運用の約束:
- 計画的なメンテナンス（Supabase の Restore など）も失敗として数える。数えないと目標が現実とずれる。
- 月初に前月の結果を見て、目標が厳しすぎる／甘すぎるなら数字を見直す。
- SLO は「人を責める道具」ではなく「リリースを続けてよいかの判断材料」。

## 今の測定結果と限界

結果は `docs/slo-dashboard.html` と提出文を参照（生成時点の実測）。

- 測定は**直近の短い時間だけ**で、30日分の SLO を評価したものではない。この数字は「仕組みが動いている」ことの確認であり、「99.5%を守れている」証明ではない。
- 実運用では probe を定期実行して記録を貯める必要がある（GitHub Actions の cron は5分間隔が下限で、遅延もある。長期の履歴は Uptime Kuma の記録が正）。**定期実行は未実装**。
- 測定地点は1か所（この PC）。回線の問題を本番の障害と誤認する可能性がある。

## 設計判断

- **数字は「守れる最も厳しい値」にした**: 理想（99.99%）ではなく、現構成で守れる値。守れたら上げる。
- **計算を純粋な関数に分けた**: 測定・計算・表示を分け、計算だけをテストできるようにした（境界: バジェットちょうど・古いデータ・データ不足）。
- **既存の監視を置き換えず役割分担した**: 通知は Uptime Kuma、数字での評価は今回、と分けた。
