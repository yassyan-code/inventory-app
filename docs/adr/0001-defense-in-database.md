# ADR-0001: 守りは「アプリのAPI」でなく「DB（RLS・トリガー）」に置く

- 状態: 採用（2026-10-19に記録。判断自体はこれまでの課題で積み上げた）
- 関連: `docs/architecture.md`（③トレードオフ）、`docs/threat-model-stride.md`、`supabase/007,010,013`

## 背景

在庫管理アプリを、小さな個人開発で、複数チームが使えるSaaSとして作っている。
- バックエンドを自前で持つと、実装と運用（落ちる所・秘密の置き場）が増える。人手は1人
- 本番の配信はRailwayの静的nginxで、サーバー処理を動かせない
- Supabaseのanon keyは、ブラウザに渡る公開情報。つまり**誰でもAPIを直接叩ける**前提で考える必要がある
- 実際に、アプリ経由でなくAPI直叩きだと「履歴を残さず在庫だけ変える」「created_byを偽る」ことが再現できた（第67課題）

## 検討した選択肢

### A. ブラウザからSupabaseを直接叩き、権限・整合性・監査はDB側（RLS・トリガー・RPC）に持つ【採用】
- 良い点: 自前サーバー不要で、運用する物が減る。API直叩きでも同じ守りが効く。守りがDB1か所に集まる
- 悪い点: 複雑な集計・複数テーブルをまたぐ処理がしにくい。DBの変更がそのままフロントに響く。ポリシーのミスが全チームに波及する。SQLの知識が要る

### B. 自前のAPIサーバー（BFF）を挟み、そこで権限チェックと記録をする
- 良い点: ロジックをコードで書けて、テストしやすい。複雑な処理や外部APIの呼び出しも置ける
- 悪い点: サーバーの運用（落ちる・秘密の管理・スケール）が増える。**DBを直接叩く道が残る限り、迂回できる**ので、結局DB側にも守りが要る（二重管理）

### C. 書き込みをすべてSupabase Edge Functions経由にする
- 良い点: サーバー側で検証でき、秘密鍵も置ける。DBを直接叩く道を閉じられる
- 悪い点: 全書き込みの作り直しが要る。Edge Functionsは未導入で、この規模には重い

## 決定

**Aを採用する。** 権限・チーム分離・整合性・監査は、DBの機能（RLS、トリガー、SECURITY DEFINER関数、権限のREVOKE）で持つ。
サーバー処理が本当に必要な部分（AIの秘密鍵）だけ、別に切り出す（将来はC）。

## 理由

1. **迂回できない場所に守りを置く**のが一番強い。BFFを足しても、anon keyでDBを直接叩けるなら迂回できる。第67課題で実際に迂回を再現した
2. 1人で運用できる量に収まる。落ちる所を増やさない（`spof.md`の方針と一致）
3. DBの守りは**ローカルのPostgres(PGlite)で実際のRLSごとテストできる**ので、SQLでも品質を保てる（9件の監査ログテスト、CIで毎回実行）

## 引き受けた代償（トレードオフ）

- ポリシーのミスは全チームに波及する → `tenant_isolation_check.sql` と PGliteテストで検査。変更はstaging→productionの順
- 入力チェックがアプリとDBの2か所になる → 最終防衛線はDBのCHECK。アプリ側は利便性のためと位置づける
- マイグレーションの適用が手動で、DB実体とリポジトリがずれうる → 適用前に同名の表・トリガーの有無を確認する（第67課題で衝突が起きた）
- 複雑な集計が要る機能が増えたら、この判断を見直す

## 見直す条件（これが起きたらADRを書き直す）

- 在庫の一括棚卸しなど、複数テーブルをまたぐ処理が増え、RLSだけで表せなくなった
- 外部サービス連携（課金・通知）が増え、秘密鍵を持つサーバー処理が多数になった → 選択肢Cへ
- チームやデータが大きくなり、DB1つの負荷分離が必要になった（`scale-bottleneck.md`）

## 結果として起きたこと（記録時点）

- 良い方: 監査ログをDBのトリガーで足すだけで、API直叩きも含めて記録できた。アプリは変更不要だった
- 悪い方: staging DBの実体とリポジトリのずれで、013が一度失敗した。命名を変えて解決
