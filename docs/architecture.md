> **改訂の経緯**: 最初に描いた版はVercelを本番だと誤認したまま公開した。実際の本番は

## ② この構成で詰め込みすぎている所

課題の問い「1か所に詰め込みすぎている所はある？」への回答。

### 見つかった詰め込みポイント

| 箇所 | 何を詰め込んでいるか | 何が起きたか |
|---|---|---|
| **`/api/chat`とホスティングの結合** | 「チャット機能」と「Vercelという特定のPaaS」が不可分に結合していた。コード上はただの1ファイルだが、実質的に「Vercelでしか動かないアプリ機能」を本体（Railwayで配信するSPA）に混ぜ込んでいた | 本番をRailwayに寄せた瞬間、チャットだけ丸ごと動かなくなった（405）。気づくまで4日以上かかった |
| **`src/lib/inventory.js`** | チーム解決（`getCurrentTeamId`）、商品CRUD、在庫増減、履歴記録が1ファイルに同居 | 現状は問題ないが、機能が増えるほど1ファイルの責務過多になっていく兆候がある |
| **`RegisterPanel.jsx`** | 入力バリデーション・Yahoo API呼び出し・登録処理・UIが1コンポーネントに同居 | バリデーションのルール（`MAX_NAME_LENGTH`等）がDBのCHECK制約と2箇所管理になっている（`handover.md`に既知の注意点として記載済み） |

### どう分けるべきか

- **チャットのような「特定プラットフォーム依存の機能」は、フロントのビルド成果物と同じ場所に置かない。** ホスティング先を選ばずに動く形（例: Supabase Edge Functions。Supabase自体は既にAuth/DBで使っており、フロントがどこで静的配信されようと同じエンドポイントを叩ける）に分離するべきだった。「配信インフラ」と「サーバー処理が要る機能」を同じデプロイ単位に混ぜたのが根本原因。
- **`inventory.js`は「チーム解決」と「在庫操作」で分割の余地がある。** 前者はセッション・権限に関わる横断的関心事、後者は業務ロジック。今は小規模なので実害はないが、次に機能を足す時の分割候補として明記しておく。

## ③ 選んだ設計のトレードオフ

課題の問い「良い点と、代わりに諦めた点」への回答。3つの主要な設計判断について。

| 設計判断 | 良い点（選んだ理由） | 諦めた点（代償） |
|---|---|---|
| **フロントから直接Supabaseを叩く**（BFFを挟まない） | 独自バックエンドの実装・保守コストがほぼゼロ。RLSさえ正しければ安全性も保てる | 複雑な集計・複数テーブルをまたぐトランザクションがしにくい。DBスキーマの変更がそのままフロントの変更を要求する（API契約がゆるく分離されていない） |
| **マルチテナントを`team_id`列＋RLSで表現**（DB分割やスキーマ分割ではない） | 1系統のDBで運用でき、バックアップ・マイグレーションが単純。初期フェーズ（数百〜数千テナント想定）ではこれで十分 | テナントごとの物理的な負荷分離ができない。1つのRLSポリシーのミスが全テナントに波及するリスクを一括で負う |
| **秘密鍵が必要な処理だけVercel Functionsに逃がす**（チャット機能） | 実装が簡単。Anthropicキーをブラウザに渡さずに済む、という当初の目的は達成できていた | **どこにデプロイするかという運用上の判断が、機能の生死に直結する隠れた依存を生んだ。** 「本番をどこにするか」はインフラ側の話のつもりだったが、実際はアプリケーション機能の可用性そのものを左右していた |

## 📸 提出：一番迷った設計判断とその理由

**判断**: 秘密鍵が必要なチャット機能を「Vercel Functionsに逃がす」という設計。

**理由**: 単体で見れば筋が良い判断だった（秘密鍵をブラウザに渡さない、実装コストが低い）。
だが「どのプラットフォームで動かすか」という、本来はアプリケーションの設計とは別レイヤーの話に、
機能の可用性そのものを握らせてしまった。結果、Railwayを本番に決めた瞬間、アプリのコードは
一切変えていないのにチャット機能だけ壊れるという、**設計判断の副作用が別の意思決定（本番の一本化）
で初めて顕在化する**という一番厄介なパターンを踏んだ。

「特定のホスティング環境に依存する機能は、その依存を明示的に管理する（設定で見える化する、
どこでも動く形に分離する）」というのが、今回得た一番の教訓。今の対処（`CHAT_ENABLED = false`で
一時停止）は応急処置であり、根本対応はSupabase Edge Functions等への移行になる。

## 補足1: レイヤーと責務

| レイヤー | 実体 | 責務 | 越えてはいけない境界 |
|---|---|---|---|
| UI | `src/components/*.jsx` | 入力・表示・画面ごとの出し分け | 「本当の権限チェック」をここに置かない（利便性の出し分けのみ） |
| ドメインロジック | `src/lib/inventory.js`, `csv.js`, `productLookup.js` | 在庫のCRUD、CSV変換、外部API呼び出しの薄いラッパー | DBの整合性はDB側(RLS)に必ず持たせる |
| ホスティング依存の機能 | `api/chat.js`, `api/_lib/chatGuard.js`（Vercel環境限定・現在無効） | 秘密鍵(Anthropicキー)を持つ処理**だけ**をここに閉じ込める | 本番(Railway)には含まれない機能であることを常に意識する |
| データ・権限 | Supabase (Postgres RLS, RPC関数) | テナント分離・書き込み権限・入力検証の最終防衛線 | フロントの検証だけに頼らない |
| 配信 | Railway (nginx) | 静的ファイル配信、セキュリティヘッダー付与、`/api/*`は存在しない | ここに秘密鍵を要する処理を混ぜない |

## 補足2: 主要ユースケースのデータフロー

### バーコード登録（新規商品）
```
カメラ/スキャナー → CameraScanner/HardwareScannerInput
  → RegisterPanel（入力バリデーション: 文字数・数量範囲）
    → productLookup.js（Yahoo API, 任意）→ 商品名の自動補完
    → inventory.createProduct()
      → Supabase: products insert（RLS: owner + 自チームのみ）
      → Supabase: stock_items insert（RLS: owner + product_idが自チームか検証）
      → Supabase: stock_movements insert（初期登録、change=初期数量）
```

### 在庫の増減（既存商品）
```
InventoryList の +1/-1ボタン
  → inventory.adjustQuantity()
    → stock_items select → 現在数を取得
    → stock_items update（RLS: 自チームのproduct_idか再検証）
    → stock_movements insert（履歴に1行追加）
```

### AIチャット（現在Railway本番では無効。Vercel環境のみ動作）
```
ChatPanel → fetch('/api/chat', Authorization: Bearer <Supabaseトークン>)
  → api/chat.js（Vercel Functionsが動く環境でのみ到達可能）
    ① getUserId() でSupabase Authにトークン照会（未ログインは401）
    ② validateMessages() で入力検証（role/文字数/件数）
    ③ createRateLimiter() で1ユーザー10分20回まで
    → Anthropic API（Claude Opus）→ 応答を返す
```

### アプリ内エラーの記録
```
window.onerror / unhandledrejection / ErrorBoundary
  → errorLogger.logError()（セッション内で件数上限・連投の間引き）
    → supabase.rpc('log_client_error', ...)
      → DB側でも文字数検証・全体レート制限（1分120件）→ error_logs insert
      → user_idはクライアント申告でなくJWT(auth.uid())から設定
```

## 補足3: セキュリティ境界（`docs/threat-model.md`との対応）

- **チーム間の境界**: `team_id` + RLS。`products`/`stock_items`/`stock_movements`すべてで、行そのものの`team_id`とJWTのユーザーが所属するチームを照合。加えて`stock_items`/`stock_movements`は「参照する`product_id`が本当にその`team_id`の商品か」まで検証（脅威#5）。
- **秘密の境界**: Anthropicキーは`api/chat.js`（Vercel、サーバーのみ）から出さない。Supabaseの`anon key`は公開情報という前提で、DB側（RLS/RPC）にすべての防御を持たせる（脅威#1, #3）。
- **配信の境界**: Railway本番のnginxがセキュリティヘッダー（CSP等）を返す（脅威#2）。Vercel側の`vercel.json`も同内容を維持しているが、SSO保護下なので実質はRailway側が守りの本体。

## 補足4: 今の設計の限界とスケール時の課題

- **ホスティング依存機能の切り出し不足**: ②で述べた通り、次の一手はチャット機能をSupabase Edge Functions等へ移し、どこで配信しても動くようにすること。
- **フロント直Supabase方式の限界**: 複雑な集計・トランザクションをまたぐ処理（例: 在庫の一括棚卸し）が増えると、RLSだけでは表現しづらくなる。
- **`/api/chat`のレート制限はサーバーレスのインスタンス単位のメモリ**。本格運用するならUpstash Redis等の外部ストアに置き換える。
- **`error_logs`に保持期間の設計が無い**。定期削除（例: 90日以上前は自動削除）をpg_cron等で足すのが次の一手。
- **1ユーザー1チーム固定**。同じチームに2人目以降を招待するフローが未実装。
- **在庫のしきい値通知が無い**。
