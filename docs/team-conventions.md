# チーム規約 v1（第69課題）

作成日: 2026-10-20。守るのは3つだけ。増やすのは、同じ指摘が3回出たとき。

## 1. 命名

- JS: 関数・変数は `camelCase`、コンポーネントは `PascalCase`（`src/components/`）
- DBの列・表は `snake_case`。JSに取り込むときに `camelCase` へ変換する（`inventory.js` の `createdAt` のように）
- 関数名は動詞で始める（`listStock`・`archiveProduct`・`findByBarcode`）。取得だけなら `get` / `list` / `find`
- SQLファイルは `NNN_内容.sql`。新しい表・トリガーを作る前に、同名がstaging・productionにないか確認する（013で衝突した実例あり）
- コメントは「何をするか」でなく「なぜそうするか」を書く（`csv.js` が良い見本）

## 2. レビューの書き方

- 最初に良い点を1つ書く。本当に良いと思った点だけ書く
- 改善は「〜してはどうでしょうか」「〜は意図したものですか？」という提案・質問の形で書く。「ダメ」「なぜ〜しないのか」は使わない
- 直してほしい点は、理由（何が困るか）と、できれば代案を添える
- 1回のレビューで求める改善は3つまで。残りは次回に回す
- 好みの話は `nit:` を付けて、直さなくてよいと分かるようにする

## 3. 「マージしてよい」の基準

- CIが通っている（lint・test・build）
- 変更の目的が1つで、PRの説明に「何を・なぜ」がある
- 権限・データに関わる変更は、DB側（RLS・トリガー）に守りがある（ADR-0001）。アプリ側のチェックだけで済ませない
- SQLを変えたときは、stagingで適用・確認してからproductionに適用する
- 大きな設計判断は `docs/adr/` に1枚残す

## 技術の選択をチームで決める進め方

感情論にしないため、次の順で進める。

1. 課題を1文で書く（例:「複数テーブルをまたぐ更新が、RLSだけでは表せない」）
2. 判断基準を先に決める（運用の手間・安全性・戻しやすさ・学習コスト）。選択肢を見る前に決める
3. 選択肢を2〜3個並べ、基準ごとに良い点・悪い点を書く（「慣れている」も理由の1つとして書いてよい）
4. 推奨を1つ出し、理由を添える。反対意見は消さずに残す
5. 決めた日と、見直す条件を書く。決めるのは期限を切った会議1回まで
6. `docs/adr/` に1枚残す（ADR-0001が見本）
