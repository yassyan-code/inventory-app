# 契約とスコープ(第82課題・想定案件)

> **これは練習用の想定案件です。** 依頼者・金額・日付はすべて例で、実在の取引ではありません。
> 契約の文面ではなく骨子です。実際に結ぶときは、専門家(弁護士・行政書士など)に確認してください。

## 想定案件

- 依頼者: 小さな店(スタッフ数人)の店主
- 依頼内容: 在庫管理アプリを導入したい。バーコードで入出庫を記録し、スタッフが複数人でスマホから使う
- 受ける側: 個人開発者
- 元にした実績: `docs/spec.md`(スキャン登録・在庫一覧・認証は実装済み)

## ① スコープ表(やること・やらないこと)

| 区分 | 項目 | 備考 |
|---|---|---|
| やる | バーコードでの商品登録と入出庫の記録 | スマホのカメラ。1Dバーコード(EAN-13等)のみ |
| やる | 在庫一覧・検索 | |
| やる | メールとパスワードでのログイン | 店のスタッフ分のアカウント発行まで |
| やる | 本番環境への設置と、操作説明(30分・1回) | |
| やる | 納品後30日間の不具合修正 | 納品時点の仕様どおり動かない場合のみ |
| やらない | 入出庫履歴の閲覧画面 | データは記録される。画面は別回(`spec.md` 5章) |
| やらない | 在庫が減ったときの通知 | 別回 |
| やらない | 店舗ごとのデータ分離(複数店舗の運用) | 現状は全員が同じデータを見る設計 |
| やらない | 既存データの取り込み(Excel等) | 依頼があれば別見積もり |
| やらない | 2次元コード・特殊なラベルの読み取り | |
| やらない | 納品後の運用代行・サーバー費用の負担 | 費用は依頼者の名義で契約する |
| やらない | 30日を過ぎた保守・OSやブラウザの更新への追従 | 保守契約として別に決める |

**線引きの考え方:** 「やる」は仕様書にあって動いているもの。「やらない」は、依頼者が言いそうで、まだ作っていないものを先に名指しする。

## ② 契約の骨子(業務委託の例)

| 項目 | 内容(例) |
|---|---|
| 何を | 上のスコープ表の「やる」項目。仕様書(`spec.md`)を別紙として添付 |
| いつまで | 契約日から4週間(例)。依頼者の確認が遅れた日数は納期に足さない |
| いくら | 一式 〇〇万円(例)。外部サービス(Supabase・ホスティング)の利用料は含まない |
| 成果物 | 動作するアプリ、ソースコード、操作説明。受け入れ確認は依頼者が7日以内に行う |
| 支払い | 着手時50%、検収後50%(例)。検収後14日以内に振込 |
| 変更時 | スコープ外の追加は、内容・金額・納期を書面(メール可)で合意してから着手する |
| 権利 | 納品物の著作権は、代金の全額支払い後に依頼者へ移す(例)。ただし受託者が元から持つ部品・ライブラリは対象外 |
| 責任 | 損害賠償は受け取った代金を上限とする(例) |
| 解約 | 途中でやめる場合、それまでの作業分は支払う |

## ③ 揉めどころと、先に書いておく一文

| 揉めやすいこと | 先に書く一文(例) |
|---|---|
| 「これも含まれると思った」 | 「本契約の範囲は別紙スコープ表に記載のものに限り、記載のない作業は含まない」 |
| 後から要望が増える | 「範囲外の追加は、見積もりと納期を書面で合意してから着手する」 |
| 確認が遅れて納期が延びる | 「依頼者の確認・回答が遅れた日数は、納期に加算する」 |
| 「完成」の基準がない | 「検収は、別紙の仕様どおりに動くことの確認をもって完了とする。納品後7日以内に申出がなければ検収済みとみなす」 |
| 納品後も無限に直させられる | 「納品後30日間は、仕様と異なる不具合を無償で修正する。それ以降と新機能は別途協議する」 |
| 外部サービスの費用・停止 | 「外部サービスの利用料と、その仕様変更・停止による影響は依頼者の負担とする」 |
| 作ったものの権利が曖昧 | 「著作権は全額支払い後に移る。受託者が元から持つ部品は対象外」 |
| 支払いが遅れる・払われない | 「検収後14日以内に支払う。支払いまで、本番環境の管理権限は受託者が保持する」 |

## この案件の注意(実際のアプリから)

- ログイン済みなら誰でも全データを読み書きできる簡易設計(`spec.md` 3章)。複数店舗や、スタッフごとの権限分けを求められたら、スコープ外として線を引く
- 本番ではAIチャットを非表示にしている。依頼者が「AI機能もある」と思い込まないよう、スコープ表に載せていない
