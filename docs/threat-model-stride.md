# 体系的な脅威モデリングとゼロトラスト（第67課題）

第54課題（`threat-model.md`）は「見つけた順」の点検だった。今回は **データの流れ図 → 信頼境界 → 4観点（なりすまし・改ざん・漏洩・妨害）で各所を総当たり** という作法に上げ、その結果から1つ実際に強化した（監査ログ）。

点検日: 2026-10-17。対象: フロント(React/PWA)、Railway(nginx)、Supabase(Auth/Postgres/RLS/RPC)、`api/*`(Vercel Functions)、Yahoo!API、Anthropic API、GitHub/Railway のデプロイ経路、開発者の手元(.env・スクリプト)。

## ① データの流れと信頼境界

```
                    ┌──────────── 信頼できない領域（利用者の端末。何でも送れる）────────────┐
                    │  ブラウザ (React SPA)                                                 │
                    │  ※ JS・anon key・Yahoo AppID は全部、攻撃者にも見える                  │
                    └──┬───────────┬──────────────┬───────────────┬───────────────┬────────┘
                    [A]│        [B]│           [C]│            [D]│            [E]│
                       ▼           ▼              ▼               ▼               ▼
              Railway nginx   Supabase Auth   Supabase REST/RPC  api/* (Vercel)   Yahoo!API
              (静的配信)       (JWT発行)       (RLSで守る)         ログイン必須      (任意機能)
                                                   │                  │
                                                   ▼                  ▼
                                             Postgres(データ)     Anthropic API
  ─── 信頼境界（ここを越えるたびに「疑って」検証する）───
  [F] 運用の経路:  開発者PC(.env) → GitHub → Railway(環境変数・デプロイ) / GitHub Actions(RAILWAY_TOKEN)
  [G] 手元のAI:    scripts/agent・scripts/rag（ANTHROPIC_API_KEY・ローカルのみ。本番データには触れない）
```

境界A〜E は「ブラウザ → サーバー」。**ブラウザは常に信用しない側**に置く（画面の出し分けは利便性、守りは必ずサーバー側）。

## ③ 最小権限・ゼロトラストの提案

「社内だから安全」とは考えず、**毎回・全員・全経路で確かめる**。

### 毎回確認すべき所（信用を持ち越さない）

| 確認すること | 今 | 提案 |
|---|---|---|
| 呼び出しごとの本人確認 | `api/*` は毎回 JWT を Supabase に問い合わせる。DB は毎回 `auth.uid()` | このまま（キャッシュで省略しない） |
| 「owner だから」の自動許可 | 書き込みごとに `is_team_owner()` を評価 | このまま。owner の操作も監査ログに残す（今回） |
| ブラウザの申告 | `user_id` は RPC 内で `auth.uid()` から設定。**`created_by` は申告のままだった** | 今回、トリガーで上書きに統一 |
| AI の出力 | 検証してから使う（第63・65課題） | このまま |

### 権限を最小にできる所

| 所 | 今 | 提案 |
|---|---|---|
| member の `stock_items` 更新 | 全列を更新できる（`quantity` 以外も） | 列単位の権限で `quantity` だけに絞る。DB に `CHECK (quantity >= 0)` を追加（#11） |
| `data_audit_log` | — | owner の閲覧のみ・追記専用（**今回実装**） |
| GitHub Actions | 既定の権限 | `permissions: contents: read` を明示し、必要なジョブだけ広げる |
| `RAILWAY_TOKEN` | アカウント全体のトークン | プロジェクト単位のトークンで足りるか検証して置き換える（#19） |
| service role キー | 手元の `.env`（staging）にあり、負荷試験の後始末で使う | 本番のキーは手元に置かない。使う処理を最小のスクリプトに限る |

### 秘密管理（鍵・トークンの置き場と更新）

| 秘密 | 置き場 | 見える人 | 更新のタイミング |
|---|---|---|---|
| `ANTHROPIC_API_KEY` | Vercel 環境変数 / 手元 `.env` | 運用者のみ | 90日ごと、または流出の疑い（利用量の急増）で即時 |
| Supabase service role | 手元 `.env`（staging）。本番は置かない | 運用者のみ | 90日ごと、または流出の疑いで即時 |
| Supabase anon key | ブラウザに配布（公開前提） | 全員 | 秘密ではない。守りは RLS |
| `RAILWAY_TOKEN` | GitHub Secrets | Actions のみ | 90日ごと、メンバー変更時 |
| `VITE_YAHOO_APP_ID` | ブラウザに配布 | 全員 | 秘密ではない。枠の消費を監視 |

流出の疑いが出たら: ①該当キーを無効化 → ②新しいキーを環境変数に入れて再デプロイ → ③`data_audit_log` と各サービスの利用ログで被害範囲を見る → ④ポストモーテム。

## ④ 今回強化したもの: 監査ログ（`supabase/013_data_audit_log.sql`）

秘密管理・権限・監査ログのうち、**一番穴が実在した監査ログ**を選んだ。下の3つは、実際に再現できた（013 を入れない状態で、member が API 直叩きで `update stock_items set quantity = 3` を実行し、履歴 0件のまま数量が変わった。他人の ID を `created_by` に書いた履歴も、そのまま入った）。

### 何をどう直したか

| 問題 | 直し方 |
|---|---|
| 履歴を残さずに在庫数を変えられる（#8）／商品マスタの変更が追えない（#10）／ロール変更が追えない（#12） | `products` `stock_items` `team_members` にトリガーを付け、**変更を DB が自動で `data_audit_log` に記録**する。誰(`actor = auth.uid()`)・いつ・どの行・**変わった列だけ**の前後の値。アプリの実装に依存しないので、API 直叩きでも必ず残る |
| 監査ログ自体を消される・書き換えられる | **追記専用**。insert/update/delete のポリシーも権限も無し。書けるのは `SECURITY DEFINER` のトリガーだけ |
| 誰でもログを見られる | 閲覧は**そのチームの owner だけ**（`is_team_owner`）。別チーム・一般メンバーは 0件 |
| `created_by` のなりすまし（#9） | ログイン中のユーザーなら、申告された値を捨てて `auth.uid()` に**上書き**（`force_created_by`）。拒否ではなく上書きにしたので、既存のアプリは変更不要 |
| ログが膨らむ | 値が変わらない更新（`updated_at` だけの変化）は記録しない |

### 確かめ方

`scripts/security/audit-log.test.js`（9件）。Supabase の `auth.uid()`・ロールだけを最小限まねたローカルの Postgres に、**本物のマイグレーション（`schema.sql` → 007 → 010 → 013）をそのまま流し**、RLS を効かせた状態で確かめる。

- member の直接更新が「誰が・10→3」として残る／商品マスタは変わった列だけ／変化なしは記録しない
- ロール変更はシステム側（`actor = null`）として残る
- owner は読める／member と別チームは 0件／authenticated は insert・update・delete が `permission denied`
- 偽の `created_by` が本人の ID に上書きされる

`npm test` に含まれるので CI でも毎回回る（RLS を壊す変更が入ると落ちる）。

### 適用手順と注意

1. staging(`rhowcziknvabdranlhvf`) の SQL Editor で `013_data_audit_log.sql` を実行 → 画面で在庫操作・商品登録が通ることを確認 → `select * from data_audit_log` に記録されることを確認
2. 問題なければ production(`noygjyxinkriupwequvt`) で実行（**アドレスバーでプロジェクトを確認**）
3. **名前の衝突（2026-10-17に発覚）**: staging には、未マージの課金ブランチ（PR#15）の旧 `011_security_hardening.sql` が適用済みで、別設計の `audit_log` と同名トリガー `trg_audit_products` が既にあった。初版の 013 は `audit_log` という名前だったため、`column "at" does not exist` で失敗した。テーブル・関数・トリガーを `data_audit_log` / `data_audit_row` / `trg_data_audit_*` に改名し、既存のものには触れない形にした。**マイグレーションは「リポジトリの master にある物」と「実際の DB にある物」がずれうる**ので、適用前に同名のテーブル・トリガーが無いか確認する。
4. **適用状況**: この作業ではSupabaseへ適用していない。ローカルのテストまで。

## 設計判断

- **記録は「アプリに頼む」でなく「DB が勝手に」やる**: 履歴の記録がアプリの別リクエストだったことが、迂回できた原因。守りは信頼境界の内側（DB）に置く。
- **拒否でなく上書き**（`created_by`）: 既存のアプリを壊さず、偽装だけを無効にできる。
- **監査ログは「見る人」を絞る**: 誰が何をしたかは、それ自体が機密。owner に限り、追記専用にして、ログが改ざんされる経路も塞いだ。
- **残したもの**: #11（数量の CHECK 制約）、#3（CAPTCHA）、#19（トークンのスコープ）は提案止まり。重大度が低い、または設定が管理画面側にあるため、次回以降に判断する。
