# ポストモーテム: 画面描画エラー（訓練）

| 項目 | 内容 |
|---|---|
| 日付 | 2026-09-25 |
| 種別 | **訓練（意図的に起こした障害）** ※実ユーザーへの影響なし |
| 環境 | ローカル開発サーバー（Supabase は受信用ダミーに接続。本番 DB には未接続） |
| 影響 | 未ログイン画面の描画が失敗。訓練のため利用者への影響はなし |
| 検知〜復旧 | 数分（検知は記録の到着で確認、復旧は1行の修正） |

## 何が起きたか

未ログイン時の画面（`src/App.jsx`）の見出しで、未定義の変数 `appConfig` を参照するバグを混入させた。
描画時に `ReferenceError: appConfig is not defined` が発生した。

## どう気づいたか

- 画面は真っ白にならず、`ErrorBoundary` が「問題が発生しました」と再読み込みボタンを表示した。
- 同時に `error_logs` への記録が届き、次の内容で原因を特定できた。
  - `source: react`（描画エラー）
  - `message: appConfig is not defined`
  - `stack` の先頭が `App.jsx` の該当箇所を指していた

## なぜ起きたか

- 直接原因: 訓練のため、定義のない変数 `appConfig` の参照を意図的に混入させた（実際の開発でよくある「未定義の設定オブジェクトの参照」を模した）。
- 根本原因（仕組みの穴）:
  1. **これまでは、アプリ内のエラーに気づく手段がなかった。** Uptime Kuma は「サイトが応答するか」しか見ず、HTML が返る限り正常と判定するため、画面が壊れても検知できなかった。
  2. **描画エラーの受け皿がなかった。** 例外が出ると画面全体が真っ白になり、利用者には何が起きたか分からない。
  3. **未定義変数を CI で止められていない。** lint は動いているが、この種のミスは警告止まりで、マージを止める設定ではない可能性がある（要確認）。

## どう直したか

`appConfig.title` を元の固定文言 `在庫管理アプリ` に戻した（1行）。

## 次どう防ぐか

| # | 対策 | 状態 |
|---|---|---|
| 1 | ブラウザの未処理エラーを `error_logs` に記録する（`errorLogger.js`） | 実装済み |
| 2 | 描画エラーで画面全体が落ちないよう `ErrorBoundary` を導入 | 実装済み |
| 3 | 同じエラーの連投・大量送信を間引き、DB を圧迫しない | 実装済み（10秒間引き・1セッション20件） |
| 4 | `008_error_logs.sql` を staging → production の順に適用する | **未実施（要対応）** |
| 5 | `error_logs` を定期的に確認する習慣・通知を作る（新規エラーで Slack/Discord に通知など） | 未実施（次の課題） |
| 6 | 未定義変数 (`no-undef`) を lint のエラー扱いにして CI で止める | 未実施（要確認） |

## 学び

- 「サイトが生きている」ことと「アプリが正しく動いている」ことは別で、監視も別に必要になる。
- 記録に `stack` があれば、ユーザーの報告を待たずに原因の場所まで特定できる。
- 今回は訓練のため、対策 4〜6 が残っている。**本番で気づけるようになるのは、4 を適用してから。**
