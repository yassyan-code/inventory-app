# 技術カルテ — 在庫管理アプリ（inventory-app）

*作成日: 2026-09-13（クロードコード部 仕組みがわかる編 第42課題・卒業課題）*

## ① 使っている言語・道具

| 分類 | 内容 |
|---|---|
| フロントエンド | React 19 + Vite 8（SPA）、PWA対応（`vite-plugin-pwa`） |
| バーコード読取 | `@zxing/browser` / `@zxing/library` |
| バックエンド | Vercel Functions（`api/*.js`、サーバーレス） |
| DB / 認証 | Supabase（PostgreSQL + Auth + Row Level Security） |
| 決済 | Stripe（`stripe` SDK、サブスクリプション課金） |
| AIチャット | Anthropic Claude API（`@anthropic-ai/sdk`） |
| テスト | Vitest |
| Lint | oxlint |
| CI | GitHub Actions（`.github/workflows/ci.yml`） |

## ② 動く場所

- **本番フロント**: Vercel（`inventory-app-topaz-iota.vercel.app`）。GitHub の push を検知して自動ビルド・デプロイ。
- **API**: 同じくVercel Functions（サーバーレス、リクエストのたびに起動）。
- **Railway**: 静的配信用に別途稼働（`inventory-app-production-64fe.up.railway.app`）。※2026-09時点でトライアル期限切れのため停止中。
- **監視**: Uptime Kuma（Railway上）が本番URLへ定期疎通。

## ③ データの保存先

- **Supabase（PostgreSQL）**が唯一の本体データ置き場。ブラウザから `supabase-js` で直接読み書き（自前APIを経由しない設計）。
- 主要テーブル: `teams` / `team_members`（マルチテナント）、`products`（商品マスタ）、`stock_items`（在庫数）、`stock_movements`（入出庫履歴）、`usage_counters`（課金メータリング）、`audit_log`（監査ログ）。
- **バックアップ**: Supabaseダッシュボードからのテーブル別CSVエクスポート、または `supabase db dump` で手動取得（第41回で手順化）。定期自動化は未実装（今後の課題）。

## ④ 守り方

- **認証**: Supabase Auth（メール確認・パスワード再設定・セッション復元）。ロールは `owner` / 一般で画面・操作を出し分け。
- **テナント分離**: 全テーブルに Row Level Security（RLS）＋ force RLS。`team_id` が一致する行しか読み書きできない。
- **通信**: HTTPS（Vercel/Railwayとも標準対応）。
- **秘密情報**: APIキー（Anthropic・Stripe・Supabase service_role）はサーバー側の環境変数のみに置き、ブラウザには渡さない。
- **不正対策**: Webhook署名検証（Stripe）、レート制限（DB固定ウィンドウ）、AIチャットの入力上限とメータリング、`audit_log`（書き込みポリシー無し＝改ざん不可）。

## ⑤ 公開・更新の仕方

```
手元でコード編集 → git push → GitHub → Vercelが自動ビルド(vite build) → 公開URLへデプロイ
```
- ブランチ運用: 機能は `feature/*` ブランチで開発し、PRでレビュー後マージ（現在 `feature/billing-stripe` が未マージでStripe課金機能待機中）。
- CIがpushごとに検査（lint・test）を実行。

## ふりかえり（仕組みがわかる編 全体）

第31〜42課題を通じて、「動くコードが書ける」から一歩進み、**IP/DNS → Web裏側 → API/JSON → DB設計 → SQL → 認証と認可 → HTTPS → 脆弱性点検 → サーバとクラウド → ログとデバッグ → バックアップ → 技術カルテ**という一連の土台を、すべて自分の稼働中アプリ（inventory-app）の実データで確認した。
