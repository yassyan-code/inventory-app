# 1台落ちても止まらない設計（第59課題・単一障害点の洗い出し）

作成日: 2026-10-06。構成は `architecture.md`、本番のRailway設定は2026-10-06時点でMCP経由で実測した値。

## ① 単一障害点（SPOF）マップ

リクエストの通り道に沿って「ここが落ちたら何が止まるか」を並べた。

```
 利用者のブラウザ
   │ ①DNS/ドメイン（現状は *.up.railway.app。独自ドメインは未設定）
   ▼
 ┌──────────────────────────┐
 │ ② Railway: inventory-app   │ ← レプリカ1台 / sfo 1リージョン
 │    nginx（静的配信のみ）     │   ヘルスチェック "/" あり
 └──────────────────────────┘
   │ アプリ(JS)を受け取ったあと、データは直接Supabaseへ
   ▼
 ┌──────────────────────────┐   ┌─────────────────────┐
 │ ③ Supabase Auth            │   │ ④ Supabase Postgres  │
 │   ログインできなくなる       │   │   在庫の読み書き全部   │
 └──────────────────────────┘   └─────────────────────┘
   ⑤ Yahoo!商品検索API（任意機能） ⑥ GitHub→Railway自動デプロイ（配信経路）
   ⑦ Uptime Kuma（監視）= 1台＋ボリューム1つ。落ちると「落ちたこと」に気づけない
```

| # | 箇所 | 落ちると | 影響の大きさ | 起きやすさ | 現状の備え |
|---|---|---|---|---|---|
| ② | Railwayのレプリカ1台 | 新規アクセスでアプリが開けない | 大 | 中（再デプロイ・コンテナ再起動で数秒〜数十秒は起きる） | ヘルスチェック、`/`が200を返すまで切替を待つ。**台数の冗長化なし** |
| ③④ | Supabase（Auth＋DB） | ログイン不可・在庫の閲覧/更新が全停止 | **最大**（アプリの中身が全部ここ） | 低〜中 | バックアップ手順は`db-backup-restore.md`。**即時に切り替わる予備はなし** |
| ① | ドメイン/DNS | URLが引けない | 大 | 低 | `*.up.railway.app`をRailwayが管理。独自ドメインは`custom-domain.md`の計画段階 |
| ⑥ | GitHub / Railwayのビルド | 新バージョンを出せない（今動いている版は動き続ける） | 小 | 低 | 前の成功デプロイが残る。壊れた版は`verify-railway-deploy`が検知。**注意**: 2026-10-06に「Wait for CI」との循環で本番が3回スキップされた（`postmortem-2026-10-06-railway-ci-deadlock.md`）。現在はCI待ちをオフにして解消 |
| ⑤ | Yahoo! API | 商品名の自動補完だけ止まる | 小 | 中 | 任意機能なので手入力で続行できる（**すでに縮退運転できる設計**） |
| ⑦ | Uptime Kuma 1台 | 監視と通知が止まる（アプリ自体は無関係に動く） | 小〜中 | 中 | 監視が静かに止まるのが怖い。監視の監視は無し |
| - | チャット(`/api/chat`) | 機能なし | なし | - | 現在`CHAT_ENABLED=false`で無効化済み（SPOFではなく無効機能） |

**一番大きいSPOFはSupabase。一番「安く潰せる」SPOFはRailwayの1台構成。** 大きさと潰しやすさは別なので、分けて考える。

### 実は効いている「止まりにくさ」
- 配信は**静的ファイルのみ**で、サーバー側に状態を持たない。複数台にしてもデータの食い違いが起きない（冗長化と相性が最も良い形）
- PWA（`registerType: 'autoUpdate'`）なので、一度開いた端末にはアプリ本体のファイルが端末側に残る。Railwayが数分落ちても、**すでに開いたことのある端末はアプリの画面までは出せる**（ただしデータはSupabaseから取るため、Supabaseが生きている必要がある）
- Yahoo!は落ちても手入力で縮退できる

## ② なくす設計（After）

```
 利用者
   │
   ▼
 ┌────────────────────┐
 │ ロードバランサ         │ ← Railwayが標準で提供（自前で作らない）
 │ （ヘルスチェックNGの台は外す）│
 └───────┬────────────┘
    ┌────┴─────┐
    ▼          ▼
 ┌──────┐  ┌──────┐
 │nginx#1 │  │nginx#2 │   ← 同じ静的ファイルを持つ2台（状態なし＝そのまま複製できる）
 └──────┘  └──────┘
    │ 1台が落ちても、もう1台が受ける
    ▼
 Supabase（Auth + DB）  ← ここは今回は「冗長化せず、備えを厚くする」（下記）
```

段階を3つに分ける（上から順に、コスト・手間が増える）。

| 段階 | やること | 潰せるSPOF | コード変更 | コスト |
|---|---|---|---|---|
| **A（今回の一歩）** | Railwayのレプリカを1→2台にする | ②（台数の冗長化）。デプロイ中の切替も途切れにくくなる | **なし**（設定のみ） | 台数分の従量課金が約2倍（静的nginxは軽量） |
| B | 同一リージョンの2台を**別リージョン**にも置く（`multiRegionConfig`） | リージョン丸ごとの障害 | なし | 追加。プラン次第 |
| C | Supabaseを有料プランへ（自動バックアップ・PITR・SLA）／障害時は「閲覧専用画面」を出す | ③④の復旧時間を短縮（冗長化ではなく復旧力の強化） | 閲覧専用の縮退UIは小改修 | 月額固定費 |

Supabase自体を2系統にする（アクティブ/スタンバイ）のは、認証・RLS・データ同期を二重管理することになり、今の規模には過剰。**「落ちない」ではなく「落ちても早く戻る・何が起きたか分かる」に倒す**のが現実的。

## ③ 今の規模で最初に打つ一手

**Railwayの`inventory-app`をレプリカ2台にする。**

- **理由**: 静的nginxは状態を持たないので、台数を増やすだけでロードバランサが振り分けてくれる。コード変更ゼロ、戻すのも設定1つ
- **効果**: 1台がクラッシュ・再起動しても、もう1台が応答する。デプロイ時の切り替わりの隙間も小さくなる
- **限界（正直に）**: 2台にしても**Supabaseが落ちたら止まる**。これで潰せるのは「Railway側の1台」だけ。一番大きいSPOF（③④）は残る
- **確認が必要**: 追加課金とプランのレプリカ上限。**未適用**（本番設定の変更になるので、承認をもらってから実施する）

### 適用後の確かめ方
1. `numReplicas`が2になり、両方のデプロイがSUCCESSになっていること
2. Railwayの管理画面で片方を止め、`/`が200を返し続けること（Uptime Kumaで確認）
3. 片方を止めた間にログイン〜在庫更新が通ること

## 次に潰す順番
1. **A: レプリカ2台**（今回の提案）
2. **⑦ Uptime Kumaの監視の監視**: 外部の無料監視（別サービス）で「Uptime Kuma自身の生死」を見る
3. **C: Supabase障害時の縮退**: 閲覧専用画面とステータス表示。復旧手順は`incident-runbook.md`に追記

## 📸 提出：単一障害点マップ＋冗長化の設計図＋設計判断の一言

**設計判断**: 「一番大きいSPOF（Supabase）」ではなく、「一番安く確実に潰せるSPOF（Railwayの1台）」から手を付ける。

**理由**: Supabaseを冗長化するのは、認証・RLS・データ同期を二重に管理することになり、今の規模ではコストと複雑さが効果を上回る。一方、静的配信は状態を持たないので、台数を増やすだけで済む。
「ここが落ちたら終わり」を全部潰そうとせず、**影響の大きさ×潰しやすさで順番を決め、潰せない所は「復旧を早くする」に切り替える**のが、今回の学び。
