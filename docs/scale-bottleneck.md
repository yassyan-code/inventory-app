# スケールの壁（第58課題）

利用者・データが増えたとき、どこが先に悲鳴を上げるかを、実際に負荷をかけて調べた。
対象: staging環境（`rhowcziknvabdranlhvf`）。実行日: 2026-10-03。
実験スクリプト: `scripts/load-test.mjs`（`node scripts/load-test.mjs`で再実行可能）。

## ① 負荷実験とボトルネックの特定

3つの経路に、同時リクエスト数を10→30→60→100と増やしながら負荷をかけた。

| 経路 | 内容 | 対照 |
|---|---|---|
| static | Railway本番の静的ファイル配信 | 詰まらないはずの対照群 |
| read | Supabase REST経由の`products`読み取り（RLSポリシー評価を含む） | 読み取りの実力 |
| write | `log_client_error`のRPC呼び出し（第54課題#3で作った、全体レート制限付きの書き込み経路） | 書き込みの実力 |

### 結果（実測）

```

n=30   p50=231ms  p95=272ms  max=273ms  エラー 0件
n=60   p50=231ms  p95=286ms  max=289ms  エラー 0件
n=100  p50=300ms  p95=344ms  max=366ms  エラー 0件

=== read（Supabase REST・RLS評価込み） ===
n=10   p50=880ms  p95=887ms  max=887ms  エラー 0件（初回のコールドスタート）
n=30   p50=106ms  p95=137ms  max=145ms  エラー 0件
n=60   p50=145ms  p95=350ms  max=364ms  エラー 0件
n=100  p50=116ms  p95=184ms  max=204ms  エラー 0件

n=10   p50=118ms  p95=124ms  max=124ms  成功10/10
n=30   p50=72ms   p95=103ms  max=104ms  成功30/30
n=60   p50=123ms  p95=177ms  max=187ms  成功60/60
n=100  p50=181ms  p95=201ms  max=205ms  成功20/100・拒否(400) 80/100
```

### 分かったこと

**static・readは、100同時アクセスまでは詰まらなかった。** レイテンシは安定し、エラーも0件。
この規模では、CPU・通信・DB読み取りのどこも先に悲鳴を上げていない。

**最初に悲鳴を上げたのは、write経路——しかも「遅くなった」のではなく「拒否され始めた」。**
4回目のバースト（n=100）で、それまでの累計リクエスト数（10+30+60=100件）が1分間の
ウィンドウ内に積み上がっており、`error_logs_rate_window`の「全クライアント合計で1分120件まで」
という制限に達して、80件が拒否された（`raise exception`→ HTTP 400）。

レイテンシ自体は write 経路でも最後まで200ms程度に収まっており、**DBの処理速度が足りなく
なったわけではない**。詰まった正体は、「全ユーザーが1つの行（カウンタ）を取り合う」という
設計そのものが生む**直列化ポイント**だった。これはCPUやメモリを増強しても解消しない種類の詰まり。

> 補足: `log_client_error`は第54課題#3で「DBを無限に膨らませる攻撃」への対策として、
> あえて全体で1本のカウンタに絞って作った。今回それが、**悪意ある攻撃だけでなく、
> 正当なユーザー増加でも同じように詰まる**ことが分かった。守りのための設計が、
> そのままスケールの壁にもなっている。

### 今回測れなかった部分（正直に書く）

`products`/`stock_items`の書き込み（チーム所属の認証ユーザーが行う実際の業務操作）は、
本物のログインセッションを大量に用意する必要があり、staging環境のデータを荒らすリスクも
あるため今回は実施していない。ただし設計上、`adjustQuantity()`は商品1件につき1行の
`stock_items`をSELECT→UPDATEする作りなので、**同じ商品に複数人が同時に操作が集中した場合**
（人気商品のセール時など）、行ロックによる直列化が起きる可能性が高いと考える。
次に測るべき候補として記録しておく。

## ② スケール方針（垂直 or 水平）

| 対象 | 詰まりの性質 | 選ぶ方針 | 理由 |
|---|---|---|---|
| `error_logs`のレート制限カウンタ | **業務ロジック上の直列化**（1行をみんなで奪い合う） | **水平**（ただし形を変えて） | マシンを強くしても「1分120件まで」というルール自体は変わらない。Postgresの1行ロックの外に出し、Redis/Upstashのような高速カウンタに**水平的に逃がす**か、カウンタ自体を複数（例: ユーザー単位）に**分割**するのが筋 |
| `products`読み取り | 現状は未検出（100同時まで健全） | 将来は**水平**（read replica） | 在庫アプリは「見る」が「変える」よりずっと多い典型的な読み取り多めのワークロード。読み取りが先に詰まるなら、書き込み用の主系はそのままに、読み取り専用のレプリカを横に足すのが素直 |
| `stock_items`の更新（未測定・推測） | 同一行への同時アクセスが起きた場合の直列化 | **垂直**がまず簡単、限界が見えたら**設計変更**(水平では解決しない) | 1つの商品の在庫数は「正しい1つの数字」である必要があり、行を分割して水平分散する発想とは相性が悪い。まずは素直にDBのスペックを上げる(垂直)。それでも詰まるなら、台数を増やす話ではなく「在庫数の持ち方」自体の設計変更（例: 増減をイベントとして積んで後で合算する）が必要になる |

## ③ トレードオフ

### error_logsのカウンタをRedis/Upstashのような外部ストアに逃がす場合
- **良い点**: 行ロックの直列化から完全に解放され、同時書き込みの上限が大きく上がる。カウンタ用途に特化しているので速い
- **諦める点**: 新しい外部サービスへの依存が増える。「Supabaseだけで完結させる」という今までの設計方針（`architecture.md`参照）を崩すことになり、障害点が1つ増える。Redisが落ちた時にレート制限をどう振る舞わせるか（止める／素通しする）を新たに決める必要がある

### カウンタをユーザー単位に分割する場合（Postgresのまま）
- **良い点**: 新しい依存を増やさずに直列化を緩和できる。1ユーザーの連投が他のユーザーに影響しなくなる
- **諦める点**: 今の設計は「未ログインでもエラーを記録したい」という理由であえてユーザー単位のキーを持たせていない（`threat-model.md`参照）。分割するには「誰の操作か」を表す安定した鍵（IPアドレス等）を新たに持ち込む必要があり、その鍵自体が偽装・共有IPでの誤検知などの新しい課題を連れてくる

### products読み取りをread replicaで水平スケールする場合
- **良い点**: 書き込み用の主系に手を入れずに、読み取りの処理能力だけを増やせる。読み取りが支配的なこのアプリの使われ方に合っている
- **諦める点**: レプリカへの反映には遅延がある（replication lag）。「商品を登録した直後の一覧に反映されない」ような、今まで気にしなくてよかった整合性の問題を新たに設計に組み込む必要が出てくる

### stock_itemsをまず垂直スケールする場合
- **良い点**: コードを一切変えずに済む。一番手間が少なく、今すぐ打てる手
- **諦める点**: スペックを上げても「1つの商品の在庫数を正しく保つ」という制約自体は消えないため、いずれ上限に当たる。その時は水平スケールではなく、在庫の持ち方（設計）そのものを見直すしかなく、先送りした分だけ後の変更が大掛かりになる

## 📸 提出：ボトルネックの特定結果 ＋ 選んだスケール方針

**特定結果**: 100同時アクセスの実験で、static配信・RLS付き読み取りはどちらも詰まらなかった。
最初に悲鳴を上げたのは、`error_logs`のレート制限に使っている**たった1行の共有カウンタ**で、
レイテンシの悪化ではなく「80%が拒否される」という形で現れた。CPUでもDBの処理速度でもなく、
**設計そのものが作った直列化ポイント**が、スケールの壁の正体だった。

**選んだ方針**: このカウンタは垂直スケール（マシンを強くする）では解決しない種類の壁なので、
**水平**に倒す——Redis等の専用カウンタへ逃がす、またはユーザー単位に分割する。
一方で読み取りが将来詰まった場合は、素直に**read replicaで水平**スケールする（読み取り
主体のワークロードに合っている）。`stock_items`のような「1つの正しい数字」を守る必要がある
箇所は、安易に水平分散せず、まず**垂直**で時間を稼ぎ、本当に限界が来たら設計そのものを見直す。

### 設計判断の一言

"詰まったら台数を増やす"と機械的に考えるのではなく、**詰まりの正体が「資源不足」なのか
「設計上の直列化」なのかを先に見分けること**が今回の学び。前者は垂直・水平どちらでも
対症療法が効くが、後者（今回のカウンタのように）はマシンを増やしても解決しない。
守るための設計（レート制限）が、そのままスケールの壁にもなり得るという事実を、
机上の想像ではなく実際に負荷をかけて確認できたのが今回の収穫。
