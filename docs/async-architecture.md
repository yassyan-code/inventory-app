# 待たせない・詰まらせない設計（第60課題・非同期アーキテクチャ）

作成日: 2026-10-08。対象コードは `src/lib/inventory.js` / `src/components/RegisterPanel.jsx` / `src/lib/productLookup.js` / `src/lib/errorLogger.js` / `api/chat.js`。
**これは設計書で、コードはまだ変えていない。** 時間は実測ではなく、`scale-bottleneck.md`（第58課題）の実測値からの推定と明記する。

## ① 待たせている重い処理を洗い出す

このアプリはサーバー側の処理が少なく、メール送信や画像処理のような典型的な重い処理はない。
その代わり、**「ユーザーの操作が、通信の完了を待っている場所」** を探した。

| # | 処理 | なぜ待たされるか（コードの根拠） | 待たされる人 | 非同期の向き |
|---|---|---|---|---|
| 1 | **スキャンして在庫+1**（`handleDetected` → `findByBarcode` → `adjustQuantity`） | Supabaseへの通信が**6回、順番に**走る（下記）。終わるまで `status === 'loading'` で**次のスキャンを無視**する | 倉庫で連続スキャンする人 | **最優先** |
| 2 | **商品名の自動取得**（`lookupProductName`） | 外部API（Yahoo!）を `fetch` で待つ。**タイムアウトの指定がない**ため、Yahoo!が遅いと登録フォームが出ない。その間もスキャンは無視される | 新しい商品を登録する人 | 高（切り離しやすい） |
| 3 | **AIチャット**（`api/chat.js`） | Claude APIの応答を最後まで待ってから返す（数秒〜十数秒）。現在は `CHAT_ENABLED=false` で無効 | チャットを使う人 | 中（再開するとき） |
| 4 | **CSV出力**（`downloadCsv`） | 全件をブラウザのメモリで変換する。`listStock` に件数の上限がない | 在庫が多い人 | 低（今は軽い。数万件を超えたら） |
| 5 | **通知**（在庫しきい値・エラー通知） | **まだ存在しない。** ポストモーテム #5（`error_logs` の新規エラーをSlack/Discordへ）が該当 | 通知を受ける人／書き込む人 | 設計の最初から非同期 |
| - | **エラー記録**（`logError`） | 呼び出し側が `await` しない「投げっぱなし」で、すでに非同期。画面を待たせていない | なし | 済（良い例） |

### #1 の中身（6回の通信）

コードを数えると、スキャン1回で次の通信が**直列**に走る。`supabase.auth.getUser()` は、呼ぶたびに認証サーバーへ問い合わせる前提で数えた。

```
スキャン
 ① products を探す                 （findByBarcode）
 ② stock_items の現在数を読む       （adjustQuantity）
 ③ stock_items を新しい数で更新する
 ④ 本人確認 auth.getUser            （getCurrentTeamId）
 ⑤ team_members でチームを調べる
 ⑥ stock_movements に履歴を書く
 → やっと画面が更新される
```

1回あたり約100〜180ms（`scale-bottleneck.md` の実測：読み取りp50 106〜145ms、書き込みp50 72〜181ms）とすると、**1スキャンあたり約0.7秒前後**（推定）。
倉庫で次々に読み取ると、この間のスキャンは捨てられる（`if (status === 'loading') return`）。**待たされるだけでなく、取りこぼす。**

さらに、②→③は「読んでから書く」ため、**同じ商品を2人が同時に操作すると、片方の増減が消える**（lost update）。`scale-bottleneck.md` で「未測定の推測」と書いた箇所と同じ原因。非同期にするとき、これを悪化させない設計が必要になる。

## ② キューで切り離す設計

「全部を非同期にする」のではなく、**効く所から3段階**で進める。

### 段階0: まず往復を減らす（同期のまま）
- 6回の通信を、DB関数 `adjust_stock` **1回**にまとめる（在庫を足す＋履歴を書く＋チームの検証を、1つのトランザクションで）
- 「`quantity = quantity + 変化量`」を1文で実行するので、**lost updateも同時に直る**
- これだけで、約0.7秒 → 約0.15秒（推定）になる。**非同期にする前に、まず減らせる往復を減らす**

```sql
-- 設計案（未実装）。RLSを効かせるため security invoker にする
create function adjust_stock(p_op_id uuid, p_product_id uuid, p_change int, p_note text)
returns int language plpgsql security invoker as $$
begin
  -- 同じ操作ID(p_op_id)を2回受けたら、2回目は何もしない（二重送信対策）
  insert into stock_operations (op_id) values (p_op_id) on conflict do nothing;
  if not found then return (select quantity from stock_items where product_id = p_product_id); end if;

  update stock_items set quantity = quantity + p_change where product_id = p_product_id;
  insert into stock_movements (product_id, change, note, team_id) values (...);
  return (select quantity from stock_items where product_id = p_product_id);
end $$;
```

### 段階1: 端末に「送信待ちの箱」（キュー）を置く
```
スキャン → 画面は即「+1（送信待ち）」 → 箱に積む → 1件ずつ取り出して adjust_stock を呼ぶ
                                                      ├ 成功 → 「確定」に変える
                                                      └ 失敗 → 間をあけて再送（箱に残す）
```
- 箱の置き場所は、PWAなので**ブラウザの保存領域（IndexedDB）**。タブを閉じても、電波が切れても消えない
- 各操作に**操作ID（番号札）**を付ける。再送で同じ操作が2回届いても、1回だけ反映される
- 同じ商品の操作は、箱の中の**順番どおり**に送る
- 送れない操作が溜まったら、画面に「未送信 N件」を出す。**黙って捨てない**
- 商品名の自動取得（#2）も同じ考えで切り離す：先にフォームを出し、名前は届いたら埋める（3秒でタイムアウト）

### 段階2: サーバー側のキューは、通知から使う
- 在庫の増減にサーバー側のキュー（Vercel QueuesやSQSなど）は**使わない**。段階0と1で足りるのに、運用する物が増えるだけ
- **通知（#5）はサーバー側のキューが向いている**。`error_logs` にINSERTされたら `notifications` テーブル（Postgresを箱として使う）に1行積み、別の処理（Supabase Edge Function + pg_cron）が取り出してSlack/Discordに送る
- こうすると、**通知先（Slack）が落ちていても、エラー記録の書き込み（`log_client_error`）は止まらない**。送信は後から再試行できる
- 送信に何度も失敗した通知は「失敗箱」へ移し、見えるようにする

## ③ 非同期にすると、体験と「詰まりやすさ」はどう変わるか

### 構成図（前と後）
提出用の図は、公開ページと画像（`第60課題_前後の構成図.png` / `第60課題_効果と設計判断.png`）にした。要点は次のとおり。

```
【前】スキャン → 画面「読み込み中…」（次のスキャンは無視）
        → ① ② ③ ④ ⑤ ⑥ と6回順番に通信 → 完了を表示

【後】スキャン → 画面は即「+1（送信待ち）」→ 端末の箱に積む（次のスキャンもOK）
        → 1件ずつ adjust_stock を1回呼ぶ → 成功で「確定」／失敗は再送
```

### 効果（推定。実測は未実施）

| 項目 | 前 | 後 |
|---|---|---|
| スキャンしてから画面が変わるまで | 約0.7秒前後 | ほぼ即時（体感） |
| 連続スキャン | 処理中のスキャンは**取りこぼす** | 箱に積むので**取りこぼさない** |
| 通信の回数 | 1スキャンで6回 | 1回 |
| 回線が不安定な倉庫 | エラーで失敗 | 溜めて、つながったら送る |
| 同じ商品を同時に操作 | 片方の増減が消えることがある | 1文で足すので消えない |
| DBへの負荷（詰まりやすさ） | 6回×人数 | 1回×人数。送信を1件ずつに絞れる |

### 代わりに引き受けること（トレードオフ）
- **画面の数字が、一時的に「確定前」になる。** 「送信待ち」の表示と、失敗したときの見せ方（未送信N件・やり直し）を作る必要がある
- **同じ商品を別の端末が操作していると、画面の数と実際の数がずれる時間ができる。** 在庫一覧を開き直すか、一定時間ごとに更新して合わせる
- **二重送信・順番・再送を自分で設計する必要がある。** 操作ID、商品ごとの順番、再送の間隔（だんだん長くする）を決める
- **「保存できた」の意味が変わる。** 画面に出た時点では、端末の箱に入っただけ。サーバーに入ったのは「確定」の表示になってから
- 箱が壊れると操作を失う。保存領域が消された場合に備え、未送信件数は常に見えるようにする

## 📸 提出：非同期に変えた前後の構成図＋切り離して何が良くなったか

**良くなったこと**: スキャンの待ち時間（約0.7秒 → ほぼ即時）、取りこぼし（あり → なし）、通信回数（6回 → 1回）、同時操作で増減が消える問題。

**設計判断の一言**:
> 「非同期にする前に、まず同期のまま往復を減らす（6回→1回）。それでも残る『待たせる・取りこぼす』だけを、端末のキューで切り離す。」
> 非同期は「待たせない」を買う代わりに「まだ確定していない状態」を引き受ける設計なので、効く所にだけ使う。サーバー側のキューは、通知のように後から再送したい処理に限る。
