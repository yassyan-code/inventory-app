# 第36課題 提出：認証と認可

## 1. ハッシュ化の体験結果

自分のPC（Node の `crypto`）で「保存のしかた」を3通り試した結果：

| 保存方法 | 実際に出た値 | わかったこと |
|---|---|---|
| 平文そのまま | `nyaan-2026` | 漏れたら即アウト。運営者も読める |
| SHA-256（塩なし） | `d6dc90bb0327…908f8da` | 同じパスワードなら誰でも同じ値になる → 事前計算表で逆引きされる |
| ソルト＋遅い計算（正しい形） | 1回目 `scrypt$b2d7c2ee…$7081b7aa…`<br>2回目 `scrypt$25921306…$faa9600b…` | 同じ「nyaan-2026」でも2回とも別の値。塩がランダムだから |

- 照合は「入力したパスワード＋保存された塩」で計算し直して一致を見るだけ。正しいパスワード→`true`、1文字違い→`false`。
- 元のパスワードに戻す処理はどこにも無い。
- 自分の在庫管理アプリは Supabase Auth が bcrypt で処理していて、自前のコードは平文パスワードをDB保存もログ出力もしていないことを確認した。

## 2. 認証と認可を自分の言葉で（メモ）

**認証（にんしょう）= 「あなたは誰？」を1回だけ確かめること**
受付で免許証を見せて入館バッジをもらうのと同じ。自分のアプリでは、メール＋パスワードを Supabase に渡して bcrypt 照合が通ると、JWT という通行証が1枚発行される。この「本人だと確かめてバッジを渡す」処理が認証。以後のリクエストは毎回この通行証で本人を示し、パスワードはもう出てこない。

**認可（にんか）= 「あなたは何をしてよい？」を操作のたびに決めること**
同じバッジでも、開くドアと開かないドアがある。この「その操作を許すか／拒むか」の判定が認可。自分のアプリは認可を3層で持っている：

1. **会社（テナント）分離** … 他社の在庫は一切見えない（RLS による認可）
2. **ロール** … `owner` は商品マスタの登録・編集・非表示ができる。`member` は在庫数の増減だけ（RLS ＋ API が owner 以外を 403 で拒む＝認可の強制）
3. **運営者** … `ADMIN_EMAILS` に載っているメールだけ、全社横断の管理ダッシュボードを開ける

画面でボタンを出し分けているのは親切なだけで、本当の認可は DB（RLS）とサーバー（API チェック）で行われる。`/api` を直接叩かれても owner 以外は書き込めない。

**核心**：認証は入口で1回、「誰か」を確定する。認可はその後ずっと、操作ごとに「この人にこれを許すか」を判定し続ける。別の仕組みなので「ログインできる（認証OK）＝何でもできる（認可OK）」ではない。

## 3. へえと思った点

同じパスワードをハッシュ化しても、塩がランダムだから2回とも別の文字列になる。それでもちゃんと照合できるのが不思議で、納得した。
