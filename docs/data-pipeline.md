# 集めて・整えて・貯める（第61課題・データエンジニアリング）

作成日: 2026-10-11。実装は `supabase/011_daily_stock_summary.sql`。
**状態: SQLを書いてローカルのPostgreSQL(PGlite)で動作確認済み。staging / production には未適用。**

## ① 貯めたいものを決める

「どこから・何を・どこへ」の3つで決めた。

| | 内容 |
|---|---|
| どこから | `stock_movements`（入出庫履歴。1操作1行の生データ）＋ `products`（商品名・カテゴリ） |
| 何を | **日×商品ごと**の入庫合計・出庫合計・差引・操作回数 |
| どこへ | 新テーブル `daily_stock_summary`（1日×1商品×1チームで1行） |

**なぜこれか**: 生の履歴は、増える一方で「先週よく出た商品は？」「今月の入庫は？」と聞くたびに全件を数え直すことになる。
夜に1日分を集計して貯めておけば、あとは小さな表を読むだけで済む（第58課題の「重い集計を毎回やらない」と同じ考え）。
将来の使い道: 売れ筋・動かない在庫の一覧、発注の目安、AIチャットへの材料。

他の候補（今回は見送り）:
- 商品ごとの最終入出庫日（動かない在庫の発見）→ 日次サマリから後で作れる
- `error_logs` の日次件数 → ポストモーテム #5（通知）と一緒に検討する

## ② パイプライン

```
集める                    整える（クレンジング）                貯める
stock_movements ─┐        ・change = 0 を捨てる                 daily_stock_summary
                 ├─ JOIN ─・日付を日本時間で区切る ─ 日×商品で ─ ・team_id + product_id + day が主キー
products ────────┘        ・商品名の前後の空白を除く    集計    ・読めるのは自分のチームだけ(RLS)
                          ・カテゴリ空 → 「未分類」             ・書けるのは関数だけ
                          ・入庫と出庫を分ける

動かす: 毎日 02:00(日本時間) に pg_cron が refresh_daily_stock_summary(3) を実行
```

- **直近3日分を「消して作り直す」**。同じ範囲を何度実行しても結果が同じ（冪等）。遅れて届いた履歴も、次の夜に正しく反映される
- 日付は **日本時間** で区切る。UTCのままだと、日本の深夜0〜9時の操作が前日に混ざる
- `security definer` の関数で、`anon` / `authenticated` からは実行できない（`permission denied` を確認済み）。アプリから集計を書き換えられない
- テーブルの読み取りはRLSで自チームの行だけ。他チームの集計は見えない

### 動作確認（ローカルPostgreSQL・テストデータ）
| 確認 | 結果 |
|---|---|
| チームAの直近3日の履歴7件（change=0 を1件含む）から集計 | 4行ができた（change=0の1件は捨てられ、牛乳の今日3件は1行にまとまった） |
| 商品名 `"  牛乳 "` の空白 | `牛乳` にそろった |
| カテゴリが空・null | `未分類` にそろった |
| 日本時間 01:00 の操作 | 同じ日に入った（UTCなら前日になる時刻） |
| 2回続けて実行 | 件数も合計も同じ（冪等） |
| 範囲外（9日前）の履歴 | 混ざらない |
| 他チームの履歴 | チームごとに別の行になる |
| `anon` で関数を実行 | 拒否された |

※ ここまでは手元のテストデータでの確認。**staging の実データでの確認はまだ**。

## ③ バッチか、ストリームか

**今作ったのは「バッチ」**（夜にまとめて定期実行）。

| | バッチ（今回） | ストリーム（流れてきた端から） |
|---|---|---|
| 仕組み | 夜に1日分を集計 | `stock_movements` に入るたび、トリガーで集計を更新 |
| 反映の速さ | 最大1日遅れ | ほぼ即時 |
| スキャン時の負荷 | **増えない** | スキャンのたびに書き込みが1つ増える |
| 失敗したとき | 次の夜に作り直せる | 取りこぼしが残りやすい |
| 作りやすさ | 簡単（SQLと予約だけ） | 順番・二重処理・再計算の設計が要る |

**このアプリにはバッチが向く。** 理由:
1. 使い道（売れ筋・月次の入庫など）は「昨日まで」で足りる。リアルタイムは要らない
2. 第60課題で「スキャンの待ちを減らす」と決めたばかり。スキャンのたびに書き込みを足すと逆戻りになる
3. 遅れて届いた履歴（オフラインの送信待ち＝第60課題の段階1）を、作り直しで自然に拾える

**ストリームにする目安**: 「在庫が閾値を割ったら、すぐ通知」のように、分単位で反応したい用途が出たとき。
それは集計ではなく通知の話なので、第60課題の段階2（`notifications` テーブルの箱）で扱う。
