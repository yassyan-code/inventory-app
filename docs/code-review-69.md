# 建設的レビューの例（第69課題）

対象: `src/lib/inventory.js`（Claudeが書いたコード）。作成日: 2026-10-20。
書き方は `docs/team-conventions.md` の「レビューの書き方」に従った。

## 良い点

`getMyMembership` の `role` を `owner` / `member` の2値にまとめ、`isAdmin` を返している点が読みやすい。
画面側が生のロール文字列を知らなくてよいので、将来ロールが増えても直す場所が1か所で済む。
`extractQuantity` に「なぜ配列と単体の両対応か」のコメントがあるのも、後から読む人に親切だと思う。

## 改善提案（1つ）

`adjustQuantity`（104〜126行目）について、次のように変えてみてはどうでしょうか。

今は「在庫を読む → 足し算する → 書き戻す → 履歴を書く」を、ブラウザから4回に分けて行っている。
このため、次の2点が気になった。

1. 2人が同時に +1 すると、両方が同じ値を読んで書き戻し、片方の増減が消えるかもしれない
2. 在庫の更新後に履歴の書き込みが失敗すると、在庫だけ変わって履歴が残らない

ADR-0001（守りはDBに置く）の考え方に合わせて、「在庫更新+履歴追加」を1つのRPC（DB関数）にまとめるのはどうでしょうか。
`UPDATE ... SET quantity = quantity + $1` なら競合せず、同じトランザクションで履歴も書ける。

確認したこと: 013の監査ログは `stock_items` の変更を記録し、010は他チームの商品を参照する行を防ぐ。
ただし、同時更新での上書きと、履歴(`stock_movements`)の書き忘れは、どちらもまだ防げていない。
これを承知のうえで今は許容する判断なら、その旨をコメントかADRに残すだけでも十分だと思います。

## 補足（任意）

`adjustQuantity` では `getCurrentTeamId()` を更新の後に呼んでいる。先に呼べば、未ログインや所属なしのときに在庫を変える前に止められる。
